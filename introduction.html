What is CList?
A personal learning and communications application that runs in your browser.
  • Read feeds and search the web
  • Annotate pages and follow the people you learn from
  • Write once and publish to Mastodon, Bluesky, WordPress, and Blogger
  • Chat and collaborate with others
CList runs in your web browser, not on a company's servers, so no single company controls it. It is built out of simple components so nobody can own it.

What you do with CList
CList is for reading, writing, and connecting with others who are doing the same.
  • Read feeds, accounts, and searches in one place
  • Write posts and publish them to the platforms you use
  • Save what you find into collections, and annotate pages as you read
  • Chat with people you find, and edit documents together
Learning happens when you read, respond, and share with others, so CList brings those activities together in one place.

Decentralized and distributed
CList has no central server. Its parts run in many places.
  • Each person runs their own copy, hosted on any web server or on their own computer
  • Services such as kvstore, collab and discussions can each run as many separate instances
  • Your CList connects only to the service instances you choose
  • Peer-to-peer chat connects browsers directly once two people have found each other
No central server is required, so no single operator can switch CList off or change its terms for everyone.

CList is made of separate parts, and any of them can be swapped out.
CList web client
Static files on any web host, or on disk

The same files for Windows, macOS, Linux
Account server (kvstore)
Encrypted accounts, login, DID documents
Annotation server
Stores your annotations; any instance works
Feed converter (opml2json)
Reads OPML lists and aggregates feeds
Cross-domain proxy (proxyp)
Reaches APIs that block browser requests
Peer discovery (discussions)
Lets chat peers find each other
Collaborative editing (collab)
Real-time shared documents
Pastebin
Publishes collections as shareable links
Third-party platforms
Mastodon, Bluesky, WordPress, Blogger, AI APIs
Each part can be replaced, so no single operator is required. You can mix and match these services using any providers you wish.

Privacy and security
Your password and encryption key never leave your browser.
  • Passwords and keys are encrypted in your browser before they reach the account server
  • The account server stores only encrypted data
  • Loading an item checks its annotation server, which sees the item's address and your IP
  • Looking up a person's identity document reveals your IP and interest to its host
  • Social platforms see your IP address and the API calls made with your own credentials
  • The project publishes its privacy notes, including known gaps
CList keeps no reading history on a server, so you decide which services to connect and can replace any of them. A copy of your data on a server is unreadable without your password, so a server breach exposes much less.

Accounts
An account is the credential CList needs to read or publish to one service.
  • Each account has a type, such as Mastodon, Bluesky, or OPML
  • Account information is encrypted locally before it is stored
  • Permission flags decide where an account is used: reading, posting, editing, and so on
Each account is a separate credential, so you can change or remove one service without affecting the others.

Your identity
Your DID is a public identifier that belongs to you, not to any one platform.
  • Your DID looks like did:web:kvstore.mooc.ca:users:alice
  • The key pair is generated in your browser, and the private key is stored encrypted
  • Your social accounts can be linked to your DID, so others can find them
A DID is an identifier you can keep even when you change keys or services, so your identity does not depend on one company's account.
In the Me panel, you choose which accounts appear in your public DID document. Chat messages are already signed with your key; signing published posts is future work.

Where CList runs
The same application can run from three places.
Hosted site
clist.mooc.ca, in any modern browser. The default, and the simplest way to start.
Desktop app
A download that starts a small local server on your computer and opens CList in your browser.
Saved files
Unzip the files and open index.html directly. No install. Logging in to a remote Account Server is not yet supported this way.
The CList client runs on any web host or on your own computer, so you are not tied to one site.
In the future we'll provide a way to clone an entire server with all the CList service applications, so you can self-host everything yourself, or provide services to your school or institution.

The CList multi-pane interface
Two main panes, with a source selector on the left and publishing controls on the right.
Left pane
Select the accounts and sources you read from.
Read pane
Read the items from the sources you selected. Send items and references from here to the write pane.
Write pane
Compose and edit. Items and references sent from the read pane appear here.
Right pane
Define where and how you publish or save what you have written.
Learning tools need to support both reading and writing, and connect both directly to the community of other people who are reading and writing too.
CList also runs on mobile; you swipe left or right to move from pane to pane.

How items are presented
Every source's items appear in the same object model, no matter what service they come from.
  • Items appear as a list of entries in one standard format
  • Each service supplies its own status actions, such as like, share, or reply
  • If a service does not offer an action, CList does not show it
A common format means you read any source the same way, and the actions you see match what each service can actually do.
A standardized object model enables interoperability between various types of data, allowing multiple types of resource to be presented in the same environment.

Loading items into the editor
Anything you are reading can be loaded into the editor. You can load multiple items from multiple sources into the same document - this is convergence of CList.
  • Load an item from the read pane into the write pane to reply to it or cite it
  • Load several items into the same post, converging many sources into the single thing you are writing
  • CList keeps a reference list of every item you load, with its URL, author, and service
Loading many items into the same document allows you to bring ideas together; it's not just a thread that breaks off into various unrelated topics.
CList keeps track of your sources for attribution. Future work will include integration with services like Zotero and automated bibliography creation.

One format for every editor
Editors exchange content as HTML or plain text, so switching editors can change your formatting. The same object model is used for all edited documents.
  • Each editor declares whether it works with HTML or plain text
  • The same post can be sent to several publishing platforms

Not all editors support all formats. The editor shows what it can, and doesn't touch what it can't.

CList is a set of static files, so you can host it anywhere that serves files.

Architecture
CList has no server of its own. Every feature that needs one uses a separate service.
  • The application is static HTML, CSS, and JavaScript
  • Services are federated: anyone can run one, and you choose which to use
  • No required bottleneck: reading and publishing work without the optional services
With no server of its own, there is no central service to fail, change its terms, or be taken over. This is the core design choice of the project.
A priority of CList is to publish the architecture as a specification so other people can build compatible services.

The services CList uses
Each service does one job. You can change any of them.
  • kvstore: stores your encrypted accounts and your DID
  • Annotations: stores your annotations
  • Discussions: lists chat sessions so peers can find each other
  • Collab: hosts shared documents
  • opml2json: parses OPML feed files
Splitting the work into small services means each can be replaced, so you are not forced to trust one operator with everything.
